# vanilla-tailwind template

A panamaview app with a plain HTML page styled with Tailwind CSS — no React, no Vue, no bundler,
and **no Node**.

```
src/main/java/com/example/Main.java     the Java side
src/main/resources/web/
  index.html                            the page — committed
  app.js                                application code — committed
  input.css                             Tailwind's entry point — committed
  tailwind.css                          GENERATED by scripts/build-css.sh
  manifest.txt                          GENERATED by scripts/build-css.sh
scripts/build-css.sh                    compiles the CSS and writes the manifest
run.sh                                  build the CSS, then run on the JVM
build-native.sh                         → target/myapp
```

## Why no Node

Tailwind publishes a standalone binary per platform, so the CSS build does not need a JavaScript
toolchain. For a template whose whole reason to exist is "I do not want a frontend build", pulling
in Node and `node_modules` to compile one stylesheet would defeat the point.

The first build fetches that binary (~80 MB) and **verifies it against the release's own
`sha256sums.txt`** before running it. A downloaded executable that nobody checked is exactly the
case worth checking. It is cached at `~/.cache/panamaview-tailwind` — a build tool, not project
content, so it is not in this directory. Override with `TAILWIND_CACHE`, pin a version with
`TAILWIND_VERSION`.

If you already have Node, you can skip the download entirely:

```sh
npx @tailwindcss/cli -i src/main/resources/web/input.css -o src/main/resources/web/tailwind.css
```

## Run it

```sh
./run.sh              # build the CSS, then run on the JVM
./build-native.sh     # → target/myapp, a standalone executable
```

**Use `./run.sh`, not `mvn compile exec:exec` directly.** The stylesheet is generated, so the CSS
build has to run first, and `run.sh` is what does that. Running Maven on its own fails with
`missing resource manifest` — true and unhelpful, which is why it is spelled out here.

## Editing

`run.sh` runs the app with live reload on, so editing `index.html` or `app.js` reloads the window.
Edits have to reach `target/classes/web` first, which happens on save from an IDE or on
`mvn compile` from a terminal.

**CSS is not part of that loop**: Tailwind has to re-scan for class names, so re-run
`./scripts/build-css.sh` after adding classes to the markup. Watch mode is available if you want it
(`build-css.sh` would need the `--watch` flag added — the binary supports it), but for a page this
size a 30 ms recompile on demand is simpler than another background process.

## Adding classes

Two things have to agree or the class silently produces no CSS:

1. **The class must be in the markup.** Tailwind generates only what it finds. Use whole class
   names in the source — it scans for strings, so a name assembled at runtime (`"text-" + colour`)
   is invisible to it.
2. **The file must be in `@source`.** `input.css` lists `index.html` and `app.js` explicitly rather
   than relying on automatic detection, so the build is reproducible. Add a file, add a line.

Both failures look the same from the app: a class in the markup with no rule behind it.

## The two flags you must not drop

Both are already in `pom.xml` and `run.sh`, and both bite in ways that do not name the cause:

- **`-XstartOnFirstThread`** — AppKit requires the event loop to own the process' first thread.
  Drop it and the window misbehaves without saying why. (A native executable does not need it.)
- **`--enable-native-access=ALL-UNNAMED`** — the calls into Cocoa and WebKit are native access.

## Adding other assets

Two places, or the file will work on the JVM and go missing from the executable:

1. `manifest.txt` is **generated** by `scripts/build-css.sh` from what is in this directory, so a
   new file is picked up as soon as the build runs.
2. `-H:IncludeResources='web/.*'` in `build-native.sh` — resources are **not** inherited from a
   dependency, so each app declares its own.

## The bridge

```js
const greeting = await java.invoke("greet", { name: "World" });   // → "Hello World"
```

```java
.bind("greet", params -> "Hello " + params.getOrDefault("name", "world"))
```

The other direction:

```java
.onReady(app -> app.postToJs(Map.of("message", "ready", "from", "Java")))
```

```js
window.onJavaMessage = (payload) => { … };
```

**Do not copy `panamaview.js` into this project.** The framework stages it into the web root at
startup, straight out of the panamaview jar, so it always matches the version you are running. It
is a reserved name there.

Reference it with a **leading slash** — `/panamaview.js`, not `panamaview.js`. A relative path
resolves against the page's own directory, so it works from `/index.html` and breaks the moment a
route adds a segment.

## Verifying without a window

```sh
./build-native.sh
./target/myapp -Dpanamaview.check=true
```

It stages the assets and reports what it found — including `tailwind.css`, because a stylesheet
that never got built is a failure that looks like a styling bug. It never opens a window, so it
runs in CI.
